# finops-dbt-duckdb

Cloud billing line items → reconciled cost marts → statistical cost-anomaly detection →
month-end run-rate projection. Built with **dbt + DuckDB**, runs entirely on a laptop.

## Quickstart

```bash
python -m venv .venv && source .venv/bin/activate   # Python 3.10-3.13 (dbt does not yet support 3.14)
pip install -r requirements.txt
make data    # 90 days of synthetic billing data
make build   # dbt seed + run + test
make eval    # detector precision / recall vs injected ground truth
make extend  # simulate 7 new billing days -> incremental load
```

## The problem this models

A FinOps team gets a raw billing export every day: thousands of line items, some duplicated by
export glitches, some negative (legitimate credits), tagging gaps on a few percent of rows. From
that, they need three things: a reconciled daily-cost table they can trust to the cent, an early
warning when a service's cost spikes outside its normal pattern, and an honest month-end
projection. This repo builds exactly that pipeline, on **synthetic** data generated by
`scripts/generate_billing_data.py` — nothing here is a real cloud bill.

## Pipeline

```
raw CSV (synthetic CUR-like export)
   ├─ stg_billing_line_items  (typed, de-duplicated, 'untagged' fallback)
   │     ├─ dim_date
   │     ├─ dim_service  ◄── seed: service_categories
   │     └─ fct_daily_cost  (incremental; grain: date × account × service × team)
   │            ├─ mart_cost_anomalies
   │            └─ mart_month_end_projection
   └─ stg_raw_duplicate_report  (source observability)
```

## Results (90 days, synthetic)

- `dbt build`: 31 tests passing, 1 intentional warning (reports source duplicate rows)
- Extending the data by 7 days and re-running incrementally gives the **same row count and
  total cost** as a `--full-refresh`
- Anomaly detector: precision 1.00, recall 1.00 on the 4 injected spikes — a sign the pipeline
  and detector work end to end, *not* evidence of real-world accuracy (see Limitations)

## Design FAQ

**Why incremental with a 3-day lookback instead of "only new rows"?**
Billing exports get restated after the fact. "Only new days" would silently miss corrections;
`fct_daily_cost` re-processes the last 3 days every run and replaces them by a surrogate key
(`delete+insert`).

**Why a reconciliation test?**
`assert_fct_reconciles_to_staging.sql` compares daily totals between staging and the fact table
to the cent. Dropped rows, bad joins, or an incremental-logic bug all fail the build immediately
instead of silently under- or over-counting cost.

**Why fix duplicates in staging but also report them separately?**
Staging keeps one row per `line_item_id` so downstream sums are correct — but silently fixing a
data-quality problem hides it. A `warn`-severity test counts duplicates per day and surfaces them
on every run.

**Why a robust (median/MAD) anomaly score instead of a fixed cost threshold?**
Cloud cost trends upward and has weekly seasonality, so a fixed threshold either fires constantly
or never fires. The model fits a trailing log-linear trend per service and day-type, then flags a
day whose residual is a large outlier relative to recent residuals (details and the known
distortion this introduces are in `mart_cost_anomalies.sql`).

**Why is the month-end projection a median run-rate, not a forecasting model?**
It's meant to be a transparent baseline a reviewer can challenge line by line — and the benchmark
a real forecasting model would have to beat.

## Known limitations

- The injected anomalies are large (2-5x) against well-behaved noise, so the 1.00/1.00 result
  demonstrates the pipeline works, not real-world detection accuracy.
- The anomaly model's OLS trend fit is not robust to an earlier large spike still inside its
  window; a Theil-Sen fit or iterative exclusion would fix this.
- Built against DuckDB for local reproducibility; targeting BigQuery/Snowflake would mainly change
  date functions and the incremental strategy.

## Repo map

- `dbt_project.yml`, `profiles.yml`, `Makefile`, `requirements.txt` — project config
- `scripts/generate_billing_data.py` — synthetic CUR-like data, with injected ground truth
- `scripts/evaluate_anomalies.py` — precision/recall of the detector vs that ground truth
- `seeds/service_categories.csv` — product_code → category mapping
- `models/staging/` — typing, de-duplication, source observability
- `models/marts/` — dimensions, incremental fact, anomaly detection, month-end projection
- `tests/` — schema tests plus singular reconciliation/quality tests
